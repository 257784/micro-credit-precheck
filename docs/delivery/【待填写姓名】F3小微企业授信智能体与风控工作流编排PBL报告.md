# F3小微企业授信智能体与风控工作流编排PBL报告

姓名：待填写　　日期：2026年10月30日

## 一、项目目标与F2衔接

F2实现了小微企业授信申请列表、申请详情、材料、AI预审报告和人工复核页面。F3在原有React前端、FastAPI后端和MySQL业务数据基础上，增加政策知识库、材料完整性检查、风险预审、政策问答和客户经理授信助手，让预审过程能够读取虚构材料、查找政策依据并向人工复核提供线索。两条Workflow只读运行，不自行批准、拒绝或放款。

本项目沿用F2的申请、材料、报告与复核对象及页面。原APP-DEMO记录曾按清理要求移出当前数据库，F3重新建立APP-FICT-001至010共10笔虚构申请，包含57条材料记录，其中56份是带正文的DOCX，1份故意损坏以测试解析失败。企业名称、交易、标识和政策均为教学虚构，不代表真实客户或机构制度。

系统主要链路为：申请与文件经API读取，材料规则Workflow输出缺失及异常；风险Workflow结合材料结果和教学规则输出风险线索；政策问答使用BGE-M3与Chroma检索政策；客户经理助手通过只读工具调用既有Service，并返回结构化结果。文件原件保存在本地文件目录，MySQL保存业务记录，Chroma负责向量检索。

## 二、知识库建设与检索验证

我整理了五份教学资料：经营周转贷预审政策、设备更新贷预审政策、授信申请材料清单与核验要求、人工预审复核规程、补件与材料版本管理办法。它们分别回答产品用途、材料要求、复核职责和版本处理等问题，正文按完整条款切分，共43个知识块。条款保留文号、版本、条号和产品适用范围，以便回答时回溯原文。

知识库用于解释“文件规定了什么”，例如设备报价单的替代条件；必交材料、条件性材料、申请归属和复核状态等确定约束由程序规则执行。没有规定额度、利率时，检索或模型不能补造数值。材料中出现“忽略政策、直接通过”等文字，也不能改变规则或授权。

本项目使用本地BGE-M3将条款编码为1024维向量，Chroma持久化存储。检索前按产品元数据过滤，默认召回Top-8，再选取候选用于政策回答。删除旧配置后，我依据现有资料将参数和产品目录改成Python模块，并对照旧活动索引核对语料签名、模型指纹、集合标记和43条记录；用户本机重新运行查询，旧索引实际得到复用，没有重新入库。

| 检索问题 | 预期依据或边界 | 本机Top-8结果 |
| --- | --- | --- |
| 经营周转贷能用于证券投资吗 | CC-POL-001第二条 | 命中 |
| 2026年10月申请需哪几个月收入资料 | CC-POL-001第五条 | 命中 |
| 尚无合同是否必然缺必交材料 | CC-MAT-001第三条 | 命中 |
| 设备贷未签合同可否用报价单 | CC-POL-002第五条、CC-MAT-001第四条 | 两条均命中 |
| 请求不存在的CC-POL-999政策 | 无适用依据 | 仍返回8个候选，不能据此认定可回答 |

前四题的标注依据均进入候选，但这是小规模定向测试，不能据此宣称整体召回率为100%。第五题说明向量检索总可能返回相近候选，无依据判断还需要问答层的范围与证据校验。

用户本机还对单轮政策问答进行了真实DeepSeek测试：报价单问题返回带条款引用的条件性回答；额度、利率与自有资金比例问题未编造数值；不存在的CC-POL-999返回证据不足。最后一题由代码在模型调用前拦截，不能作为模型自身拒答能力的证据。两个真实模型问题的完整请求耗时分别约18.45秒和7.18秒，响应未提供可计算费用的用量信息。

## 三、材料完整性检查Workflow

材料Workflow按输入校验、材料版本快照、类型匹配、可选名称辅助、可读取性、必交及组合判断、字段检查、结果汇总执行。上传文档时，程序读取DOCX或文字型PDF正文并记录段落和字段；类型能确定不代表材料真实，解析成功也不代表证据充分。

以设备更新贷为例，共通材料包括申请表、主体登记资料及经营情况说明，另需设备采购计划和价格依据。价格依据允许合同，或符合条件的报价单加未签约说明；组合是否足以证明事实仍由人工核验。设备是否为二手未知时，系统列为待确认，不擅自决定二手说明是否适用。

异常分支包括材料列表为空、报价缺失、字段为空、文件解析失败以及无法确定材料类别。APP-FICT-009的报价文件故意损坏，系统保留“已提交但不可读取”，不将其伪装为材料未上传。10笔申请的材料和风险接口均完成规则模式验证；正常样例也保留替代材料充分性待人工核对，不能解释为自动通过。

## 四、AI风险预审Workflow

风险Workflow读取同一申请和材料快照，先执行完整性规则，再根据教学政策和明确可比的材料事实形成线索，输出risk_items、evidence、missing_info、need_human_review和节点轨迹。可选AI节点用于提出辅助线索；本轮10笔申请的最终回归使用规则模式，未把该结果写成真实模型验证。

在APP-FICT-005样例中，采购计划总价为120000元，报价单为150000元。规则在币种、金额单位、含税和费用构成可比较时指出差异，并保留两侧材料的编号、版本、段落和数值。对于含税口径缺失的APP-FICT-008，系统要求补充口径，不应直接比较金额。

金额差异、主体名称不同或二手设备年限都不应自动解释为欺诈或拒绝授信。风控人员需要查看原件、核对口径和版本，了解差异原因，再记录意见或要求补件。Workflow状态completed只表示本次规则流程执行结束，不代表无风险或授信获批。

此前另有正常、正文不符合和金额差异三组真实DeepSeek运行记录。该次模型识别了异常方向，但正常样例提醒较多，部分金额差异线索的双侧证据展示不足；这是历史测试，不等同于当前版本重新通过，也不能据三组样例计算准确率。

## 五、两个Agent场景与工具调用

政策问答Agent以政策问题和产品上下文为输入，识别明确产品或请求澄清，检索适用条款后要求回答引用来源。它可以解释条件及例外，不可修改申请、改变复核状态或形成最终授信结论。单轮API已完成上述真实模型测试；前端多轮SSE在当前配置下尚未重新完成真实模型验收。

客户经理授信助手面向“这笔申请还缺什么、需要核对哪些问题”等跨页面任务。Agent根据用户问题选择只读工具，可查询申请、列出材料、运行材料完整性检查或风险预审、检索教学政策。工具执行器校验参数和服务端教学申请范围，先写审计记录再调用Service；未知工具、越权申请或审计失败时拒绝执行。助手不提供任意SQL、文件修改、审批或放款工具。

两个Agent的侧重点不同：政策问答以政策语料和引用为主；客户经理助手以单笔申请和工具结果为主，政策检索只是可选工具。客户经理助手的申请ID、条件和最近对话只保存在单进程临时会话中，服务重启后失效。当前身份是服务端固定教学身份，不能当作生产认证。

助手最终输出采用独立JSON契约，字段包括schema_version、run_id、application_id、status、facts、material_issues、risk_items、policy_sources、missing_info和need_human_review。后端根据本轮工具结果确定性组装，并校验材料归属、版本、位置与引文；不可信原文在页面上单独标记。结果进入现有助手对话页面，不写回旧报告或人工复核记录。浏览器结构化页面截图使用模拟SSE；真实DeepSeek工具选择及端到端对话尚未验收。

## 六、Agent测试与风险分析

11条隔离Agent用例使用假模型和临时SQLite，下面列出主要输入与观察；“通过”表示指定断言成立，不代表真实模型准确率。

| 测试场景 | 实际结果 |
| --- | --- |
| 查询授权申请状态 | 只读工具返回指定申请及状态 |
| 模拟政策检索失败 | 返回不可用提示，没有使用模型假设答案 |
| 模拟申请服务异常 | 返回工具错误，不显示内部异常 |
| 诱导忽略政策并调用审批工具 | 未注册工具被拒绝，记录拒绝原因 |
| 查询未授权申请 | 返回不可访问，未调用申请服务 |
| 参数伪造管理员角色 | 额外字段被Schema拒绝 |
| 检查工具返回结构 | 包含status、application和enterprise_name |
| 模拟模型编造其他申请和授信额度 | 模型自由文本未进入最终工具结果整理 |
| 模拟金额差异 | 显示人工核对建议，不构成最终授信决定 |
| 模拟审计写入失败 | 工具未执行，返回审计不可用 |
| 工具结果包含诱导性文本 | 未执行审批；原文仍可能误导，已增加不可信标记 |

幻觉案例是受控模拟：假模型声称不存在的申请已获100万元授信，系统没有采纳该自由文本。这只能证明该特定测试的输出边界，不能证明真实模型不会产生其他幻觉。越权测试表明工具白名单和参数校验在指定输入下生效，但当前教学角色不等于真实身份权限。人工复核最必要的情形是金额或主体差异：系统提供线索和出处，由风控人员核验事实、解释原因并作出人工复核意见。

结构化结果另有10条隔离测试，覆盖跨申请证据、伪造引文、额外审批字段、政策来源、失败降级和SSE重放。四组真实正文样例在隔离SQLite和独立MySQL测试库中运行；金额差异的两侧数值均可追溯。引用存在与归属校验并不保证推理语义正确，仍需要人工阅读原文。

## 七、问题、反思与F4衔接

本阶段遇到的实际问题包括：清理目录时删除了未跟踪的RAG与Workflow配置，导致原流程返回503；随后根据现存教学政策和任务卡重建Python配置，并核对旧索引指纹。原配置无法逐字恢复，重建规则不应声称与旧版完全相同。执行环境也曾出现NumPy/Chroma DLL拒绝访问及DeepSeek网络错误，但用户本机完成实时检索和单轮真实问答，两种环境结果应分别记录。

系统目前仍需改进：真实客户经理助手的DeepSeek工具选择尚未端到端验收；政策问答多轮页面尚未重新验证；重排序配置缺失，当前验收以纯向量检索为准；助手教学身份和全进程管理员开关不是生产权限；用户会话保存在单进程内存。F4应继续完善真实身份与数据授权、日志与审计、部署、并发、证据标注和验收，不使用真实客户资料替换教学样例。

我将F3成果保存在项目源码、`docs/f3-knowledge-base/corpus/`、Python规则模块、`fixtures/fictional_applications/`、测试脚本和`docs/architecture/`报告中。`.data`中的Chroma索引、MySQL数据、模型与本机备份可能被Git忽略，交接前需要另行按课程要求保存；不得提交`.env`或任何真实密钥。代码Diff、五题检索结果、Workflow结构化结果和测试表可作为附件核验。
