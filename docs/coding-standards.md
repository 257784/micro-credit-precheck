# F2 代码规范

规范的目标是让业务规则容易找到、改动容易验证。新代码遵循本文件；调整旧代码时保持行为不变，单独提交格式化改动。

## 注释和文档

- 公共模块、数据加载函数和有业务含义的类写简短 docstring：说明职责、输入输出或失败条件。
- 注释解释“为什么”：例如报告证据必须属于同一申请、处理失败不能当作无风险。不要把代码本身翻译成注释。
- 修改业务规则时，同步更新注释、`docs/data-contract.md` 和相关测试。过期注释比缺少注释更容易误导。
- 复杂接口的数据字段、状态和错误响应写在文档及模型里；页面中只保留与交互有关的简短注释。
- 示例：`# 防止报告引用其他申请的材料，避免页面混入错误证据。`。不推荐：`# 遍历材料。`

## Python 后端

- 4 空格缩进，UTF-8，建议每行不超过 100 字符；函数与变量用 `snake_case`，类用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`。
- API 层只处理请求、响应和 HTTP 错误；数据读取与对象关联放在 `app/data.py`；响应结构放在 `app/models.py`。
- 公共函数标注参数和返回类型。金额使用整数元，避免浮点金额计算；时间保留时区信息。
- JSON 样例在加载时校验 ID 唯一性和跨对象引用。新字段先改模型和数据契约，再改样例、页面和测试。

## React 前端

- 2 空格缩进，单引号，语句末尾分号；组件用 `PascalCase`，普通函数和变量用 `camelCase`。
- 请求错误、加载中、空列表、解析失败和无报告均提供明确文案；不能把请求失败或无报告显示为“无风险”。
- `useEffect` 中的异步请求在卸载或切换申请时取消，避免旧请求覆盖新详情。
- 文件变大到难以一次理解时，按职责拆分列表、详情和报告组件；不要为了缩短行数而拆出无业务含义的组件。

## 样例与提交

- `mock_data` 中只用虚构教学数据。报告证据必须引用同一申请的材料，知识条目须包含 ID 与版本。
- 每次提交前运行：`python -m unittest discover -s tests -v`、`npm run build`、`git diff --check`。后端和前端在不同目录启动时，还要检查 `/api/health` 与申请页面。
- 功能改动和大面积格式调整分开提交，便于检查真实逻辑变化。

## 自动化工具的下一步

后端建议用 Ruff 统一检查和格式化，前端建议用 ESLint 检查问题、Prettier 统一格式。安装时把依赖加入各自项目并更新 `uv.lock` / `package-lock.json`，然后让检查命令在本机和 CI 中运行。当前仓库尚未安装这些工具，因此不能把它们写成已经生效的门禁。
