# 真实文件双 Workflow 自动测试报告

后续更新：用户授权后已完成三组真实DeepSeek测试，调用均成功。结果及质量问题见 [真实模型测试报告](12-真实模型三组材料测试.md)。本文“未调用模型”描述的是当时的规则测试范围，不代表后续测试状态。

## 结论

本机实际文档上传、解析和两个Workflow的规则路径可正常执行。正常组通过可自动核验的完整性检查；内容不符合组指出缺失字段；金额差异组在材料完整的同时指出风险线索。所有结果均要求人工核验，不作授信批准。

真实DeepSeek没有调用，本报告不将规则验证冒充模型效果验证。

## 材料与操作

`mock_data/document_cases/normal/`包含六份完整DOCX及同源文字PDF：申请表、主体登记资料、经营说明、采购计划、供应商报价单、未签约说明。企业及登记标识均为虚构教学设定。`invalid_content/`为只有产品介绍的报价单；`amount_difference/`为150000元报价单。异常组替换正常组的报价单，其余五份保持不变。DOCX和PDF选一种上传即可。

使用独立申请APP-DOC-NORMAL、APP-DOC-CONTENT、APP-DOC-AMOUNT，从材料页选择类型并上传文件。设备新旧属性按计划确认，选择“否”，然后运行材料检查与风险预审。未知条件不会自动免交材料。

## 证据与复现

运行 `python scripts/check_project.py` 执行回归。运行 `python scripts/verify_document_workflows.py` 使用临时存储上传磁盘文件并调用真实ASGI接口，结果保存至 `workflow-evidence/document-results.json`，不调用模型、不污染本机记录。

浏览器脚本 `scripts/browser_document_check.py` 使用本机Edge及8017/5177测试端口；启动后端到8017，前端BACKEND_URL指向8017并启动到5177。脚本上传正常组到APP-DOC-NORMAL并操作两个Workflow。截图：`workflow-evidence/document-material-page.png`、`document-risk-page.png`。

## 发现并修复的问题

1. SQLite连接未关闭导致Windows清理失败：明确关闭连接，复测通过。
2. 新申请使旧测试固定数量四条失效：原演示断言限定APP-DEMO，筛选测试使用实际集合大小。
3. PDF初版字体编码产生提取乱码：嵌入字体并压缩子集后，关键字段提取通过；pypdf仍有扩展字符映射警告，本样例正文已测试。
4. 风险流程固定认为没有结构化事实：已接入上传原件字段，正常组可以completed，异常组保留缺失及差异。

## 限制与未通过项

- DOCX渲染脚本缺pdf2image，本机Word COM未注册：DOCX正文已解析验证，但未完成Word版式检查。六份同源PDF已逐页检查，无遮挡；它们不是DOCX版式转换。
- pypdf依赖已声明，本机6.15.0可用。uv缓存错误及随后网络限制导致uv.lock未能更新；联网环境需在backend执行 `python -m uv lock` 和 `python -m uv sync`。未验证新机器安装。
- 解析针对明确“字段名：内容”模板，不支持任意版式、OCR或原件真实性鉴别。生成PDF需要开发环境PyMuPDF和微软雅黑字体；运行系统不需要它们。
- 实际上传正文已进入可选模型证据输入，但未调用真实DeepSeek，不宣称AI准确率验证通过。
- 目前上传字段风险核对覆盖设备样例，经营周转收入核对仍需人工。completed只代表执行完成，不代表无风险或授信获批。

因此可以确认所列真实文件与本机环境下两个规则Workflow正常执行；上述限制不能写成全项通过。
