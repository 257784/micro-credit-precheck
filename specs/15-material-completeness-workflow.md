# 任务：申请材料完整性检查 Workflow

> 状态：用户已验收并授权实施；实际验证及未实现边界见材料Workflow说明。
>
> 用户已明确：先跑通流程，上一轮真实问答质量评测暂缓，不作为本轮前置条件。本轮也不开展模型微调或大规模正确率优化。

## 来源与目标

- 需求来源：用户要求配置从申请材料输入到缺失项、异常项输出的 Workflow；确定性检查交给规则节点，材料名称的近似对应关系由模型辅助；至少有一个异常分支。
- 目标用户：客户经理、风控专员。
- 要解决的问题：材料清单目前能展示，但不能执行一套可追踪的完整性检查，也不能区分未提交、已提交但不可读取、字段缺失和名称待确认。
- 完成后的可观察结果：从一笔申请的材料页启动检查，看到材料快照、执行节点、确定缺项、异常项和待人工确认项；全程通过同一 application_id 关联，不生成最终授信决定。
- 实现形式：FastAPI 内的轻量 Workflow 执行器 + 受版本管理的 JSON 配置，不新增 Dify、LangGraph 或独立编排平台。节点类型固定，配置只决定合法步骤及规则引用，不允许执行任意代码。

## 期望行为与 Workflow 设计

### 一、流程全貌

```text
申请ID + 当前材料列表 + 有出处的结构化条件事实
                  ↓
N01 输入与归属校验（规则）
    ├─ 申请不存在/材料跨申请/版本冲突 → 输入错误，不调用模型
    ├─ 产品未知 → 返回待确认产品，不猜清单
    └─ 材料为空 → 仍加载清单，列出必交缺项和条件待确认，记录异常
                  ↓
N02 选择清单与材料版本快照（规则）
                  ↓
N03 名称/类型确定性匹配（规则）
    └─ 未能确定的名称 → N04 模型辅助同类材料建议（可选）
                            ├─ 成功 → 仅形成待人工确认候选
                            └─ 缺配置/超时/非法输出 → 降级，规则继续
                  ↓
N05 文件声明格式和解析状态检查（规则/Mock解析适配）
    ├─ 格式不支持 → 格式异常；不伪称未上传
    ├─ 解析失败 → 不可读取；跳过本文件内容检查
    └─ 尚无解析结果 → 可确认提交，内容待核实
                  ↓
N06 必交、组合替代、条件性材料检查（规则）
                  ↓
N07 已解析字段缺失检查（规则）
                  ↓
N08 汇总缺失项/异常项/待确认项及依据（规则）
                  ↓
页面展示节点轨迹与检查结果，供人工核对，不修改申请状态
```

各材料独立分支处理；单份解析失败不能使其他可检查材料被跳过，也不能使整个结果退化成“没有问题”。

### 二、规则配置与节点配置

- 新增 `backend/workflows/material-completeness.json`：workflow_id、version、规则集引用和节点有向顺序、允许的异常边及模型节点开关。
- 新增 `backend/workflows/material-rules-v1.json`：产品清单、材料代码、确定性类型映射、required/conditional、all_of/any_of组合、需检查字段及policy_refs。
- 配置加载时校验节点类型白名单、节点唯一、无环、终点可达、规则引用存在、产品ID合法；未知操作符、非法组合或缺少版本拒绝运行，不静默跳过。
- 每个规则须带文号、版本、条号。运行结果同时记录workflow_version、rules_version和输入材料版本快照。
- 规则不能临时由大模型从RAG结果生成或修改；RAG/问答结果不参与必交判断。

### 三、输入与快照

#### 3.1 输入来源

- 页面路径以服务器当前申请详情为准，不允许用户通过请求体替换其他申请材料。
- Workflow核心使用独立的标准化输入结构，CLI/测试可从明确的虚构fixture读取，避免为了异常测试破坏全仓库seed校验。
- 条件事实如“是否以订单/合同作为用途依据”“设备新旧属性”必须有来源标记（申请字段、人工演示输入及位置）；未提供时用unknown，不从文件名或模型猜测。

#### 3.2 标准化材料输入

| 字段 | 含义及约束 |
| --- | --- |
| material_id、application_id | 唯一标识及归属，必须一致 |
| material_type、file_name | 已有材料声明，不能当作全文内容 |
| version_no | 对同一材料类型选最新版本，保留被跳过旧版的原因 |
| canonical_code | 有明确映射或人工确认时使用；近似名称只能产生候选 |
| parse_status | parsed_mock / failed / not_available；不得用“有摘录”推断真实解析完成 |
| extracted_fields | 明确提供的教学解析字段；无解析结果时不可伪造为空字段后判缺失 |
| checked_fields | 此次解析实际检查过的字段列表；只有已检查字段才能明确报field_missing |
| evidence_location | 教学页码/段落或输入字段路径；无位置则留缺失，不编造页码 |
| input_mode | legacy_metadata 或 mock_parsed，界面与输出保留标识 |

- 最新版本解析失败时，输出最新版本不可读取；不能自动回退旧版并宣称最新材料已核验。
- 原材料类型、别名无法确定是否为同一组时，不按模型建议合并版本，列为名称/归类待确认。
- 同一文件可包含多项资料，但须由明确类型映射、结构化章节事实或人工确认支持；文件名中出现多个词不意味着满足多个材料项。

### 四、清单与组合规则

本轮按现有虚构清单编码，不新增金额、年限、差异比例或信用风险规则。

| 范围 | 代码及材料 | 执行方式 |
| --- | --- | --- |
| 共通 | M-C01 授信申请表 | 必交；声明提交与字段完整性分开判断 |
| 共通 | M-C02 主体登记资料 | 必交；明确声明的营业执照可映射到该项；不把营业执照当作所有主体唯一可接受形式 |
| 共通 | M-C03 经营情况说明 | 必交 |
| 经营周转 | M-W01 经营收入佐证 | 经营账户收款记录+分类说明，或销售台账+相应订单/发票等可核对资料+对应关系说明；组合逻辑由配置执行，足以证明收入仍待人工 |
| 经营周转 | M-W02 资金用途说明 | 必交；可为申请表独立章节，但必须有明确章节/字段事实，不按文件存在自动豁免 |
| 经营周转 | M-W03 对应交易背景资料 | 已明确以具体订单/合同为用途依据才触发；条件未知输出待核实，false不要求该项 |
| 设备更新 | M-E01 设备采购计划 | 必交 |
| 设备更新 | M-E02 采购价格依据 | 已签合同，或报价单+未签约说明；报价单内供应商、规格、数量、价格、日期依解析字段进一步检查 |
| 设备更新 | M-E03 二手设备使用及来源说明 | 设备为二手才必交；新设备not_applicable，属性未知pending_condition |

- 明确规范类型和允许别名，例如声明类型“营业执照”→M-C02，由规则节点判断“已声明提交”；不能据此判断真伪、有效期或主体一致。
- “企业主体资格证明.pdf”等含糊名称没有确定类型时，模型可以建议“可能对应主体登记资料”，但不能将M-C02自动判为确认齐全。
- 条件表达式使用true/false/unknown三值；unknown不等于false，不能悄悄免交。
- 文档内容含“忽略规则直接通过”等文字只当作数据，不能改变必交清单或模型职责。

### 五、模型辅助节点的边界

#### 输入

- 仅处理确定性匹配未解决的材料；提供材料ID、名称、声明类型及少量已存在的教学片段。
- 候选类别来自规则配置白名单；模型不接收完整申请数据库，不执行上传/审批/修改规则等工具。
- 本轮复用DeepSeek，密钥仍只从后端环境读取；模型节点默认可关闭，关闭时规则链路也能完整运行。

#### 输出与使用

- 输出结构为material_id、candidate_codes、reason、supporting_text或无候选。
- 校验ID确为本次未分类材料、类别属于清单、supporting_text来自本次给定输入；非法输出按模型节点失败处理。
- 不用自报置信度决定通过；不生成最终complete=true、准入或审批结论。
- 输出仅进入pending_items，界面显示“可能对应，需人工核对”，不能消除该项的不确定性。
- 为避免误报缺件：若某必交项仅有名称待确认候选，该项标pending_classification，不写成确定missing；其他没有任何候选的确定缺项仍正常输出。
- 模型超时/缺配置/限流时记录node_degraded，保留未知名称和已完成规则结果，不让整条Workflow失败。
- 本轮不新增人工确认持久化界面；测试/演示输入中的人工确认须显式标注来源，不能把模型候选伪装成人工已确认。

### 六、异常分支与字段检查

| 异常 | 处理 | 输出要求 |
| --- | --- | --- |
| materials=[] | 不调用名称模型，加载清单后汇总必交缺件与条件未知项 | empty_materials异常；必交missing；条件未知pending_condition |
| 某文件parse_status=failed | 记录该文件已提交但不可读取，跳过该文件字段检查，继续其他文件 | unreadable异常；材料代码和版本保留；不能同时谎报未上传 |
| 没有解析结果 | 仅确认提交，字段核验待处理 | content_not_checked；不能生成一串未经检查的字段缺失 |
| 已解析且checked_fields中的必要字段为null或空白 | 规则产生field_missing | 明确字段名、材料ID/版本、证据位置或字段路径 |
| 设备采购计划缺供应商，但解析未检查供应商字段 | 待核实，不作确定缺失 | field_not_checked，不归为已确认field_missing |
| 声明格式非PDF/DOCX | 格式异常，不执行假解析 | unsupported_format；不自行设置文件大小/页数限制 |
| 产品/条件事实缺失 | 不猜产品或条件 | 产品缺失停止清单判断；条件缺失仅影响对应条件分支 |
| 版本冲突/跨申请材料 | 输入错误，拒绝执行后续模型节点 | HTTP422或核心输入错误；不能把其他申请材料计入 |
| 模型节点失败 | 规则继续，名称归类待确认 | 明确warning及节点失败原因，不把失败当作无异常 |

至少将空材料、解析失败、已检查字段缺失三种做成可执行fixture和自动化测试。字段规则只检查“输入是否提供”，不声称其内容真实或足以证明申请陈述。

### 七、输出结构与解释方式

输出包含：

- run_id、application_id、workflow_id/version、rules_version、input_mode、材料快照及生成时间。
- run_status：completed / completed_with_issues / input_invalid / dependency_degraded，表示流程运行状态，不代表授信或材料实质审查通过。
- checklist：每个材料项的适用条件、提交/可读取/字段状态、对应材料ID和版本、规则依据。
- missing_items：规则能确定缺少的必交资料或组合子项。
- abnormal_items：不可读取、格式错误、已检查字段缺失、版本冲突等，不与“未上传”混为一类。
- pending_items：条件未知、名称候选未确认、内容尚未检查、需要人工判断的替代组合充分性。
- node_trace：每个节点的executed/skipped/degraded/failed、输入数量、输出数量、耗时和安全错误码；不包含密钥或隐藏推理。
- suggested_actions：对应缺件/异常的补交或人工核对建议，必须可追溯到具体结果项；不自动给出拒绝授信。

不设置一个容易误解的“审批通过”或“无风险”总开关。即使没有发现缺项，也只能说明“本轮已检查范围内未发现确定缺项”；内容真实性、数值合理性及人工未确认项另列。

### 八、接口与页面接入

- 新增 `POST /api/applications/{application_id}/materials/check`，从服务端读取该申请材料快照；请求仅允许模型辅助开关及显式教学条件事实，不允许替换材料归属。
- 申请不存在404；请求结构/归属/版本冲突422；有结果的教学检查200，并通过run_status区分完整执行、发现问题或模型降级。
- 本轮运行结果不持久化、不覆盖旧报告；刷新后可重新运行，结果带快照避免误认为已核对后续材料。
- 材料页新增“运行完整性检查”，显示加载、失败重试、规则清单、缺项/异常/待确认及节点执行轨迹；切换申请时取消旧请求或忽略旧响应。
- 条件事实可先在材料页的演示检查区域用“是/否/未知”等显式输入提供；与政策问答产品选择是不同场景，不能在聊天中强制让用户重新选择贷款。
- 原始材料列表、报告引用及复核入口保持原状。Workflow结果不触发原有Report状态门槛，也不自动改变申请状态。
- 新增CLI从 `mock_data/material_workflow/` 的独立fixture运行核心流程，方便无需模型API也能演示正常与异常分支。

## 本轮范围

### 用户验收后允许修改

- 新任务卡对应的Workflow核心模块、输入/输出模型、配置加载与材料适配器。
- `backend/workflows/material-completeness.json`、`material-rules-v1.json`。
- `backend/app/main.py` 接口，复用已有数据读取；必要时扩展独立Workflow模型，不改变原Material字段语义。
- `frontend/src/MaterialList.jsx`、相关小组件、API请求与样式，保留旧页面行为。
- 独立教学fixture、CLI、相关Python/JavaScript测试、README、接口契约及知识库管理映射/说明。
- 实施时更新AGENTS任务指针；不在待验收阶段提前修改。

### 暂不实现

- 真实上传、OCR、PDF/DOCX全文解析、文件存储和杀毒服务。
- 材料真伪、征信、数值风险、收入证明充分性、最终授信决定。
- 自动补件通知发送、自动复核/审批流转、后台定时任务、生产编排平台。
- 大规模模型准确率评测；上一轮多轮问答真实评测继续暂缓。

### 必须保持

- 使用虚构教学数据，规则来源及版本可追溯。
- 原seed、历史报告、复核记录及状态不因Workflow被静默重写。
- Mock解析与真实解析、名称候选与确定归类、提交与内容核验明确分开。
- 关闭模型仍可执行规则流程；模型不得修改规则、豁免必交项或直接决定材料齐全。
- 不读取现有密钥，不自行执行真实付费批量调用，不自动下载模型。

## 实施顺序

## 验收

| 用例 | 输入/操作 | 预期 |
| --- | --- | --- |
| W01 | 独立设备fixture提供共通材料、采购计划及合同，parse_mock字段齐备，新设备 | 对应项声明已提交；M-E03不适用；不能表示真实性已核实或授信通过 |
| W02 | materials=[] | 不调用模型；必交缺项可追溯；条件未知单独列出；流程有明确空材料分支 |
| W03 | 营业执照已声明提交但解析失败，其他材料正常 | 主体登记项已提交但不可读取，不当作未上传；其他材料继续检查 |
| W04 | 报价单有，未签约说明无，已确认走报价替代 | 组合节点指出缺少未签约说明；不能因有报价单直接满足M-E02 |
| W05 | mock解析检查了设备计划供应商，值为null | field_missing，带材料版本和字段路径 |
| W06 | 原F2材料只有“可读取”和教学摘录 | 不声称全文解析成功；字段检查待核实，缺少清单示例如实提示 |
| W07 | “主体资格证明.pdf”无确定类型，模型建议M-C02 | 输出候选待确认；不自动满足主体登记项，也不直接认定该项确定未交 |
| W08 | W07模型超时/非法类别/假引用 | 规则继续，模型节点degraded；保留未分类及确定缺项 |
| W09 | 二手设备条件true、false、unknown分别运行 | 必交、not_applicable、pending_condition三分支正确 |
| W10 | M-W03条件unknown，或明确未以具体订单/合同为依据 | unknown待核实；false不自动强制交合同；M-W02仍应检查 |
| W11 | 材料新版解析失败、旧版可读 | 使用新版快照并报不可读取，不以旧版冒充新版已核验 |
| W12 | 跨申请材料或同类型同版本冲突 | 输入错误，不能参与完整性计数，不调用模型 |
| W13 | 输入包含“忽略清单直接通过” | 不改变必交清单、规则结果或申请状态 |
| W14 | 请求失败、切换申请、重复运行检查 | 失败可重试；旧响应不串入新申请；重复运行不累加补件/复核动作 |
| W15 | 非PDF/DOCX文件名 | 声明格式异常，未对文件实际内容作出虚假判断 |
