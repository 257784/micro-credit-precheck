>
> 实施记录：会话、路由、要点流及聊天界面已接入；99条Python、13条JavaScript与构建通过。真实DeepSeek质量和本机浏览器联调尚待执行，详见 `docs/f3-knowledge-base/management/08-多轮政策对话与流式验收.md`，不据替身测试认定真实回答效果通过。
>
> “流式回答”采用服务端实时接收模型流、完整回答要点及引用校验后逐条推送的方式。不是前端打字动画，也不是直接展示未校验的 token。首次可见要点仍需等待该要点和证据完整生成。

## 来源与目标

- 需求来源：用户对已运行的政策问答提出反馈：强制选择适用产品不符合普通用户的认知；应支持对话中识别需求、追问澄清、多轮承接和流式展示。
- 目标用户：不了解产品名称、希望按自身用途咨询虚构政策的客户经理、风控专员及教学用户。
- 要解决的问题：当前只能单次问答；缺 product 就停止；用户必须自行判断贷款类别；答案生成完成前只能等待。
- 完成后的可观察结果：用户仅通过对话输入需求，系统识别或澄清本次讨论范围，承接后续问题，在生成过程中逐条展示经过引用校验的回答，并能停止、重试和开启新对话。
- 边界：帮助理解政策适用范围，不判定用户符合准入、不承诺贷款可获批、不写入申请或复核状态。

## 当前行为

### 已核实事实

- `frontend/src/PolicyQa.jsx` 包含必选产品下拉框、问题输入、重排序复选框；只保留最近一次 response，无对话记录。
- `backend/app/policy_models.py` 的 `QuestionRequest` 为 question、product、rerank；`POST /api/policy/ask` 是单轮 JSON 接口。
- `backend/app/policy_qa.py` 缺 product 时要求选择产品；按单一产品召回8条，默认前6条送入 DeepSeek；重排序可选。
- `backend/app/deepseek_client.py` 以 `stream=False` 请求，完整 JSON 返回后校验引用，才交给前端。
- 当前引用检查验证来源存在和 quote 与正文匹配，不验证解释的语义充分性。
- 用户展示的回答把经营周转贷的 M-W03 与共通条款中的“设备价格依据”一起列出，说明仅有文档级产品过滤还不足以避免回答中的产品内容串用。
- 现有语料为五份虚构教学文件、两个产品；既有业务数据与申请复核链路独立。

### 未确认信息与本轮取舍

- 本轮按本机、单后端进程的教学演示实现，不设计生产账户、共享会话或多进程会话一致性。
- 对话会话先保存在后端内存；刷新可通过会话 ID 恢复，后端重启或超时后会话不可恢复，需明确提示。跨重启持久化本轮暂不做。
- 不以模型自报的置信度作为产品已确认或政策适用的证明。
- 需要用户验收的关键取舍：采用“要点级流式”，不采用未经校验的逐 token 展示；采用临时会话，不保存跨重启聊天历史。

## 期望行为与实现方案

### 一、前端对话交互

1. 移除必选产品下拉框；主界面由消息记录、输入框、发送、停止生成和新对话组成。首次输入不依赖任何产品字段。
2. 重排序开关不放在主对话流程；默认关闭，保留在开发评测/高级设置入口，不要求普通用户理解模型参数。
3. 用户消息和助手消息依次排列，历史答案不会因输入下一条问题而消失。助手澄清也是消息，用户直接输入自然语言回答。
4. 当前讨论范围可作为只读提示显示，例如“当前按设备更新相关政策解释”；不是要求点击确认的选择器，也不展示内部产品 ID、相似度或路由分数。
5. 引用编号在每条助手消息内独立有效。DOM 锚点使用 message_id + source_id，不能让第二轮的 S1 跳到第一轮原文。
6. 每条助手消息展示生成中、完成、已停止或失败状态；失败提供重试，新对话清空当前会话关联并中止在途请求。

### 二、多轮上下文如何实现

#### 2.1 后端管理上下文

- 前端只发送当前用户输入及 conversation_id，不接受客户端提交 system 消息或伪造的助手历史。
- 后端创建不可预测的随机 conversation_id，维护消息和结构化讨论状态。会话 ID 是本地会话能力凭证，不代替生产鉴权，不放在共享链接中。
- 浏览器用 sessionStorage 保存本标签页的会话 ID；刷新后从后端恢复消息。新标签页默认新会话。
- 本轮会话空闲30分钟过期；内存最多50个会话、单会话最多20个已完成轮次，达到上限提示开启新对话，不静默丢失聊天。数值为教学工程限制，不是授信规则。
- 生成提示仅使用最近6个完整轮次，且历史文本合计不超过12000字符；超限按整轮移除最早内容，不从条款正文中截断。完整已完成记录仍可在本会话界面回看。
- 当前结构化状态单独传入：讨论范围、用户明确提供的用途/日期/设备属性、待澄清项、事实来源的用户消息 ID。
- 每项提取事实同时保存原文片段。后端检查片段确实来自对应用户消息，做日期等字段的格式校验；原文匹配不等于事实已核实，也不能代替对提取语义的测试。产品路由标记 explicit_name、explicit_use、inherited 或 unresolved，便于区分明确名称、用途解释和沿用上下文。
- “用户说过的事实”不等于经材料核实的事实；不要把助手推测写成用户已确认事实。日期等缺项也不能从当前系统时间推算。
- 旧答案和旧引文不是新证据，每轮须对本轮问题重新检索当前活动索引。新轮的 S1 重新分配，不能直接引用旧轮 S1。

#### 2.2 承接、改写和纠正

- 对“那二手设备呢？”等省略问题，结合当前状态改写为独立检索问题，例如“设备更新贷采购二手设备需要什么附加资料？”。保留原问题及改写供调试评测，不把改写当成新事实。
- 改写中引用的事实须能追溯到用户输入；无法确认指代时先问“你指的是设备采购，还是刚才提到的经营周转用途？”。
- 用户明确纠正时，最新明确说明优先，例如“刚才说错了，是采购原材料”；清除原用途相关的产品范围和设备专属待问项，按新用途重新识别、检索。
- 用户另提新问题但没有改变原用途时，保留已明确的上下文；不得每轮重复追问同一个产品。
- 长历史已移出模型上下文且结构化状态未覆盖的细节，不假装记得，补问确认。

#### 2.3 并发、停止与重试

- 同一会话同时只处理一轮；第二个在途请求返回409。不同会话状态隔离。
- 每次发送带 request_id。相同 ID 的在途请求返回409，已完成请求返回已保存终态事件，避免重复生成/计费；失败后重试使用新 ID，并关联 retry_of。
- 用户消息和待澄清事实的提取记录可保留；助手失败/停止内容可显示为未完成，但不得作为已完成回答进入后续模型历史。
- 仅在最终完整响应校验通过后提交助手完整轮次与最终路由状态，再发送 done。若网络在提交后中断，可恢复后端已保存结果，不能重复生成。
- 新对话/停止后旧请求的迟到事件不得追加到新会话；前端校验 conversation_id、request_id、message_id。

### 三、自动识别产品与澄清如何实现

#### 3.1 使用可维护的产品目录

- 新建 `backend/policy-products.json`，集中维护产品 ID、显示名称、明确别名及适用范围依据（文号、版本、条号）。目前仅登记经营周转贷与设备更新贷，依据来自现有正文，不新增业务准入规则。
- 用于路由的简述必须有原文出处，不把产品介绍、few-shot 或验收答案导入 corpus。
- 路由候选由目录生成，输出 ID 必须存在且能映射到检索元数据。增加产品仍须更新目录、元数据适用关系和测试，不声称放入新文档就自动完成所有接入。

#### 3.2 路由顺序

1. 明确产品名/文号、可直接消歧的用户纠正先按确定性规则处理。
2. 有已明确讨论范围、当前没有纠正或比较意图时，可沿用该范围；信息冲突先澄清。
3. 对用途描述、模糊指代或产品选择请求，调用 DeepSeek 做结构化意图识别，输入当前用户问题、有限历史、产品目录及原文范围说明。
4. 输出结构包括 intent、candidate_product_ids、resolved_product_id、standalone_question、facts_with_message_ids、missing_slots、clarification_question。后端校验枚举、来源消息 ID 与事实是否由用户提供；不能让模型通过自由文本改写系统过滤条件。
5. intent 为 policy_question、product_discovery、comparison、common_rule、clarification_needed 或 out_of_scope。分类不执行政策准入判断。
6. 不根据单个词“合同”“报价单”直接确定产品；不会因为向量第一名属于某产品就认定用户适用该产品。

#### 3.3 三种检索路径

| 识别结果 | 检索及回答方式 |
| --- | --- |
| 已明确单一产品/明确单一用途 | 后端保留产品元数据过滤，再召回8条、选6条；自然语言说明当前解释范围，用户可随时纠正 |
| 询问产品区别或不知道该了解哪种产品 | 先读取目录指向的用途/范围条款；需要进一步向量检索时对各候选产品分别检索，按产品分组展示依据；最终上下文仍不超过6条，不能跨组拼成一套申请要求 |
| 共通流程问题，例如“客户经理能不能完成复核？” | 仅检索当前目录中所有产品均适用的共通条款；不为通用问题强行追问产品 |

对于产品比较，单一相关性排名不能吞掉另一产品的全部依据：先为每个比较产品保留至少一条范围依据，再去重补充，附属原文仍需按来源引用。当前只有两个产品，本轮验收覆盖双产品比较。

#### 3.4 澄清策略

- 信息不足且影响回答分支时，只追问当前最关键的一项。允许一句话询问用途差异，不把产品选择变成一长串资格问卷。
- 如果问题可给出有依据的条件性解释，可以先解释共同结论，再问缺失事实；不能一遇未知就完全停止回答。
- 无法判断产品时，问用户“资金主要用于日常备货/经营周转，还是购置、更新设备？”，而非“请选择 working_capital/equipment”。
- 用户回答“我也不知道”时，依据原文解释两类用途，再请求描述资金准备怎么使用；仍不明确时保留未确定状态，不默认选一个。
- 连续两轮澄清仍无新增有效事实时，说明现有知识库能解释的范围，给出可补充信息示例，不循环重复同一句问题。
- 产品能确定但设备新旧属性未知、申请日期未知时，追问该事实，不能再次询问产品。
- 用户用途同时涉及两类产品、或出现目录外用途时，提供范围说明并澄清主要用途；不能强行套入当前两类贷款。
- 路由服务失败、非法 ID 或非法结构时返回可恢复错误或确定性的用途澄清，不随机路由、不将故障包装成政策依据不足。

#### 3.5 解决当前回答中的产品内容串用

- 生成提示明确区分“当前产品专属要求”和“共通规则中的不同产品举例”。
- 已明确经营周转用途时，不能把共通段落中的“设备价格依据”写成当前用户必须解决的缺口。
- 共通条款同时提到两产品不意味着整条都要逐句复述；引用和解释应对应本次问题。保留相同的原文校验，另加入上述行为的人工验收题。
- 不通过修改原文或把所有共通条款排除来掩盖串用问题。

### 四、流式回答如何实现

#### 4.1 流式链路

```text
浏览器 POST 对话消息（fetch + AbortController）
    ↓
FastAPI StreamingResponse（text/event-stream）
    ↓ 状态事件：理解需求 / 澄清 / 检索政策
DeepSeek Chat Completions：stream=true，接收上游 SSE
    ↓ 按数据帧提取 delta.content，不转发推理内容
增量解析 JSON 中的完整 statement 对象
    ↓ 来源、quote、结构及职责边界校验通过
向前端推送 statement 事件，追加要点及证据
    ↓ 上游正常结束、完整 JSON 和全部要点再次校验
提交完整轮次，发送 done
```

- 上游仍采用结构化 JSON 回答；服务端维护有大小上限的增量缓冲，按 JSON 字符串转义、对象和数组边界解析完整要点。不使用简单花括号正则截取，必须处理引用原文里的花括号、转义引号和跨网络分片的中文。
- 每个 statement 同时包含解释与 evidence；只有对象完整并通过现有引用校验，才发往页面。sources 在 statement 之前发送，本轮来源之后不得变更。
- 不把完整答案生成后再逐字分发伪装成实时流；验收必须能观察到上游尚未结束时已出现至少一条通过校验的要点。
- 复杂场景要点很长、或只有一条要点时，仍可能在较晚阶段才出现正文；状态事件提供进度但不等同于正文生成。
- 澄清问题可作为独立终态事件发送，不为营造流式效果拆字延时。

#### 4.2 SSE 事件约定

每个 data 为单行 JSON，以空行结束事件，包含 conversation_id、request_id、message_id 和递增 seq。文本换行由 JSON 转义，事件顺序固定；前端按完整 SSE 事件而非网络 chunk 解析。

| 事件 | 数据含义及前端动作 |
| --- | --- |
| meta | 确认会话/请求/助手消息编号；允许前端显示已收到 |
| status | stage 与简短用户文案，例如理解需求、检索政策、正在回答；不包含隐藏推理或模型分析过程 |
| scope | 当前讨论范围及是否尚待澄清；仅为解释范围，不表示符合准入 |
| sources | 本轮候选来源，带 source_id、文号、版本、条号和正文 |
| statement | 已通过结构和引用校验的完整要点；按 statement_index 追加或去重 |
| clarification | 自然语言追问及 missing_slots；不显示未校验的路由 JSON |
| warning | 可选重排失败后改用向量原序等可恢复信息 |
| done | 最终业务 status、完整结果、引用集合与耗时；本轮正式完成的唯一标识 |
| error | 安全错误码、可恢复说明、已展示要点的处置方式；没有 done 即未完成 |

- 定期发送 SSE 注释心跳，防止中间代理因无输出断开；心跳不计入答案。
- 不输出 API 凭据、上游原始错误、隐藏思维链或完整 system prompt。

#### 4.3 中断、异常和回滚

- 上游超时、HTTP错误、JSON非法、未知引用、原文不匹配、超长缓冲或非正常结束：发 error，保留候选供查看，所有已流出的要点统一标为“本轮未完成，不能作为完整回答”，从正式答案区撤回，调试记录可留失败标记。
- 部分要点校验通过不代表最终整轮已通过。完整 JSON 出现重复键、结构冲突、越权字段或与已发要点不一致时，整轮失败，不提交助手成功历史。
- 网络断开或用户停止时，前端 AbortController 中止读取；后端检测断连并关闭上游连接。不能承诺已发生的上游计算或费用会撤销。
- 单轮初始建议总预算120秒，包含识别和生成；上游读取另有空闲超时，缓冲最多1 MiB。超时必须可恢复，不无限等待。
- HTTP200之后的流内故障用 error 事件表达；浏览器不能只凭 HTTP200 或收到第一段正文就认定成功。
- 未收到 done 的 EOF 视为中断，保留原问题及重试入口，不能自动补一个成功状态。

### 五、接口与兼容策略

保留现有 `POST /api/policy/ask` 单轮接口及 CLI，避免破坏既有测试和调用。新页面使用独立对话协议：

| 接口 | 用途 |
| --- | --- |
| `POST /api/policy/conversations` | 创建会话，返回 conversation_id 和过期信息 |
| `GET /api/policy/conversations/{id}` | 恢复该会话消息、状态、讨论范围及在途轮次信息 |
| `POST /api/policy/conversations/{id}/messages/stream` | 提交 question、request_id、可选 retry_of，返回 SSE；不接受 product、系统提示或任意历史 |
| `DELETE /api/policy/conversations/{id}` | 结束并清除本会话；幂等，不修改业务申请数据 |

- 请求非法422；读取或提交到未知/已过期会话404；DELETE 对已结束或不存在会话仍返回204以保持幂等；同会话并发409；达到限制返回明确可恢复状态。流开始前可用普通错误响应，流开始后用 error。
- 会话恢复返回的来源与引用属于各自消息，不把历史来源自动并入新一轮证据池。
- 单轮响应模型可以复用，但需要新增对话、路由与流事件模型；字段调整同步更新接口契约及测试。
